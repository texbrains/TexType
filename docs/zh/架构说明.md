# TexType 架构说明

2026-11-23

## 1. TexType 是什么

TexType 是 Office 和 WPS 里的公式工具，由 VisualTeX 的加载项和 LaTeXSnipper 合并后重写。

- 加载项：在 Word、PowerPoint、WPS 文字、WPS 演示里插入和编辑公式，支持 Windows 和 macOS。
- 主程序：轻量的公式编辑器，带公式识别和设置，定位类似 MathType。
- 只做桌面版，不做网页版。

## 2. 要求

1. 设置只有一份，主程序和加载项共用。
2. 用户不做任何配置就能插入公式。
3. 公式格式之间的转换只有一个接口。TexType 自己的 OLE 公式有完整、成熟的数据格式。
4. 安装包小。
5. 以后可能闭源，产品里不放妨碍闭源的东西。
6. 公式识别用合作方的 MathCraft 引擎。它的公式模型是 Pix2Text 公开的模型（见第 13 节）。
7. 不兼容两个旧产品的公式格式。初期提供一键转换，成熟后删掉。
8. MathType 兼容：
   - 我们插入的 MathType 公式，MathType 用户能直接编辑，看到的字形和 MathType 自己插入的一样。
   - 能读别人的 MathType 公式。
   - 编号格式等设置按 MathType 自己的方式保存，不丢信息。
   - 支持 MathType 6.0 和 7.0。
   - 不用 MathType 的排版引擎，只用它的字体。排版自己写，做轻量的。
9. 各部分分开。改哪里就只动哪里，不打补丁。
10. 简单好用优先。

## 3. 结构

```text
加载项        在 Office / WPS 里运行，只操作文档
   │          向主程序发请求
主程序        轻量主程序，同时是加载项背后的服务（Rust + Tauri 2）
   ├── 界面     运行在主程序的窗口里：编辑器、主窗口，以及公式的排版
   └── 核心库   被主程序直接调用：公式格式、转换、设置、识别
```

界面和核心库互不调用，都由主程序连接。

### 加载项 `hosts/`

| 目录 | 语言 | 负责 |
|---|---|---|
| `hosts/windows/Word` | C# | Word 和 WPS 文字：把主程序给的公式插入、替换、删除；编号，引用，MathType 的编号域；功能区 |
| `hosts/windows/PowerPoint` | C# | PowerPoint 和 WPS 演示：把主程序给的公式放成形状，写标签，在文本框里插入原生公式（OMML）；功能区 |
| `hosts/windows/Shared` | C# | 两个加载项共用：连接主程序、线程调度、功能区图标 |
| `hosts/windows/OleObject` | C++ | OLE 公式对象：保存公式记录和预览图，负责显示。双击由加载项捕获并打开编辑器，对象本身不处理（两个项目都是这样） |
| `hosts/macos/office-vba` | VBA | Mac 版 Word、PowerPoint 加载项 |
| `hosts/macos/wps-js` | TypeScript | Mac 版 WPS 加载项 |

加载项只调用 Office 的对象模型。格式转换、排版、设置都向主程序要。

### 主程序 `app/`

Rust 写，窗口用 Tauri 2，Windows 和 macOS 都用它。窗口里显示的是 `ui/` 的界面。Tauri 的配置在 `app/tauri.conf.json`，产品名和标识必须和 `product.toml` 一致，检查脚本会核对。

| 模块 | 负责 |
|---|---|
| `sessions` | 接收加载项的所有请求（编辑、转换、识别），分发，取消，返回结果 |
| `editor_window` | 打开公式编辑器，给用户用，或编辑加载项传来的某个公式 |
| `render` | 一个不显示的窗口，在里面运行 `ui/kernel`，做 LaTeX → MathML 和 LaTeX → SVG（和 VisualTeX 一样）。转换请求需要这两步时由它完成，其余由 `core/convert` 完成 |
| `recognition` | 截图、图片识别成 LaTeX，管理模型 |
| `shell` | 主窗口、托盘、快捷键 |
| `install` | 安装、检查、修复加载项，处理 MathType 字体 |
| `automation` | MCP 服务，让本机 AI 读写文档里的公式 |
| `platform` | Windows 和 macOS 做法不同的部分 |

### 界面 `ui/`

| 包 | 负责 |
|---|---|
| `ui/kernel` | 公式结构和编辑规则，自研排版引擎，LaTeX 转 MathML（用 MathJax） |
| `ui/editor` | 公式编辑器：工具栏、符号和模板面板、源码视图。主窗口和加载项用同一个 |
| `ui/app-ui` | 主窗口：识别、设置、加载项状态 |

依赖方向：`kernel` ← `editor` ← `app-ui`。

### 核心库 `core/`

| 部分 | 负责 |
|---|---|
| `core/formula-format` | TexType 公式格式（见第 7 节） |
| `core/convert` | 唯一的转换接口：Word 原生公式（OMML）、MathType 对象、图片格式（SVG 转 EMF、PNG），都经过 TexType 公式记录转换；MathType 预览图的排版也在这里 |
| `core/mathcraft` | 公式识别引擎 |
| `core/settings` | 设置 |
| `core/protocol` | 主程序和加载项之间的消息，产品名称和标识 |

### 旧格式读取 `legacy-import/`（不在核心库里）

读两个旧产品的公式，只给“一键转换”用，是临时的。

- 放在核心库外面，只依赖核心库。
- 主程序里只有 `app/src/legacy.rs` 用它，而且是可选功能：不带它也能编译，每次检查都会这样编译一遍。
- 以后删除：删掉 `legacy-import/`、`app/src/legacy.rs`，再删掉 `app/Cargo.toml` 里的一行依赖和一个功能开关。其他代码不用动。已经在副本里试删过，能正常编译。

## 4. 通信

加载项向主程序发请求，主程序返回能直接写进文档的内容：TexType OLE 对象的数据和预览图、图片、OMML、MathType 对象数据。加载项拿到后只负责放进文档。

| 加载项 | 通道 |
|---|---|
| Windows 的 Word、PowerPoint、WPS | 命名管道 |
| Mac 的 Word、PowerPoint | AppleScriptTask 加文件交换，VisualTeX 现在就是这样 |
| Mac 的 WPS | 本机 HTTP（127.0.0.1），由主程序提供，VisualTeX 现在就是这样 |

- 消息只在 `core/protocol` 定义一次，三种通道传的是同样的消息。
- Windows 上不再用本地 HTTPS 服务和证书（VisualTeX 现在用 43127 端口的 HTTPS 服务）。
- 主程序在登录时后台启动（VisualTeX 现在 Windows 用启动项，Mac 用 LaunchAgent）。加载项发现主程序没在运行时，自己启动它。

## 5. 排版

| 画什么 | 谁排版 |
|---|---|
| 编辑器里的公式；TexType 自己的 OLE 公式和图片公式 | 自研 TeX 排版引擎，`ui/kernel` |
| Word 原生公式 | Word 自己。我们只写出 OMML |
| MathType 对象的预览图 | 自己写的 MathType 排版引擎，`core/convert` |

```text
TexType 公式     LaTeX → 公式内核 → 自研 TeX 引擎 → SVG → core/convert 转成 EMF / PNG → 加载项放进文档
Word 原生公式    LaTeX → MathJax 转成 MathML → core/convert 写出 OMML → Word 排版
MathType 公式    LaTeX → MathJax 转成 MathML → core/convert 生成 OLE 对象（公式数据 + 预览图）→ 文档
```

编辑器和插入的图片用同一个引擎排版，编辑时看到什么，插入的就是什么。

MathJax 只做 LaTeX 到 MathML 的转换，不排版，也不画图。自研引擎不认识的命令，在编辑器里按原文显示；要放进文档的图片则拒绝生成，并说明是哪个命令，和 VisualTeX 一样。

MathML 是描述公式结构的标准格式，不决定字符位置。

### 自研引擎和 MathJax 的对比

MathJax 只能显示，不能编辑：没有光标位置，没有点击定位，处理不了输入到一半的公式。编辑器必须有自己的排版。

1000 条 arXiv 公式的测试（im2latex-100k 随机抽取，965 条在真实 LaTeX 里有效）：

| | 自研引擎 | MathJax 3.2.2 |
|---|---|---|
| 能画出来 | 97.5% | 98.1% |
| 宽度和 LaTeX 完全一致 | 92.2% | 1.3% |
| 宽度差不超过 0.1 em | 96.3% | 15.7% |
| 高度差不超过 0.1 em | 99.8% | 77.9% |

MathJax 和 LaTeX 的差别来自四处：上下标没有专门的小号字体，分式两侧多留空，表格外侧不留边距，厘米等长度不随字号缩放。

自研引擎的问题：

- 不支持环境外的 `\\`、自定义宏（`\newcommand`、`\def`）、老式 plain TeX 写法、`\mbox` 里的旧文字命令。
- 公式里夹的文字（`\mbox`、`{\rm …}`）只有 55% 和 LaTeX 完全一致。
- 发布一个月，只有一个人维护。

测试只比了整体宽高。合作方用的是 MathJax 4，数字可能不同。

## 6. MathType

MathType 公式在文档里是一个 OLE 对象（类名 Equation.DSMT4），TexType 写入的也是这个对象，不是图片。对象由两部分组成：

- 公式数据：对象里的 Equation Native 数据流，MTEF 格式，MathType 双击打开时读的就是它。`core/convert` 读写，格式和 MathType 6、7 保存的相同。不认识的记录原样保留。编解码器是自己写的，不是移植：以 MathType 自己为准（同一个公式 MathType 自己存的数据、它导出的 MathML、MathType 6 和 7 打开我们写的公式）。
- 预览图：Word 显示和打印时用的图（WMF），Word 不会为了显示去运行 MathType。这张图由自己写的轻量排版引擎来画，规则照 MathType 的，字体用 MathType 的。不调用 MathType 的程序，用户装了 MathType 也不用它画。MathType 用户双击编辑后，MathType 会用自己的引擎重画这张图。
- 字体：MathType 的 18 个 Design Science 字体随安装包附带，不从网上下载（可选的 Tiger 字体不带）。Windows 和 Mac 都装。
- 编号和文档设置：用 MathType 自己的域（MTPlaceRef、MTEqn、MTChap、MTSec）、书签、字符样式 MTEquationSection 和文档属性 MTEqnNumsOnRight。
- 引擎还没做到的结构，先用自研 TeX 引擎的 Times 方案画。这些公式的预览图和 MathType 画的不一样，达不到第 2 节“字形一样”的要求，是临时办法。另一种做法是这类公式暂时不允许插入成 MathType 格式。选哪种还没定。
- 插入方式（Windows）：把对象打包成 Word 或 PowerPoint 的文件包再插进去，不需要任何 MathType 程序。两个产品现在都这样做：VisualTeX 的 `MathTypeWordOpenXml.cs`（Word）和 `PowerPointFormulaService.MathType.cs`（PowerPoint，先放进一个临时演示文稿），LaTeXSnipper 的 `MathTypeWordPackage.cs` 和 `MathTypePowerPointPackage.cs`。
- 双击：和 VisualTeX 一样，双击 MathType 公式打开 TexType 的编辑器。设置里可以改成双击打开 MathType（只在装了 MathType 时有效；没装时总是打开 TexType 的编辑器）。
- MathType 对象只在 Windows 上插入，Mac 上不能插入。Mac 上文档里的 MathType 公式只要显示正常（靠附带的字体），不读取、不编辑、不转换。

## 7. TexType 公式格式和转换接口

完整定义见英文文档 `docs/FORMULA-FORMAT.md`。格式是对照两个项目的代码定的：VisualTeX 的 `FormulaMetadata`（OLE 对象里的 `VisualTeX.Formula.json`），LaTeXSnipper 的 `FormulaMetadata` 和 `FormulaTypography`（schema 3）。

### 放在哪里

| 容器 | 平台 | 内容 |
|---|---|---|
| Word、WPS 文字里的 TexType OLE 对象 | Windows | 公式记录和两张预览图，存在对象的数据流里 |
| PowerPoint、WPS 演示里的 TexType OLE 对象 | Windows | 同上；另外在形状标签里存一份记录 |
| PowerPoint、WPS 演示里的图片公式 | Windows、Mac | 公式记录存在形状标签里，图片就是预览 |
| Word 里的图片公式 | Windows、Mac（Mac 版 Word 不能运行我们的 OLE 对象） | 公式记录存在图片的标题和替代文字里（和 VisualTeX 一样；读屏软件会读出编码，见第 13 节） |

### OLE 对象

类名 `TexType.Formula.1`。数据流和 VisualTeX 的对象一样分三个：

| 数据流 | 内容 |
|---|---|
| `TexType.Formula` | 公式记录，UTF-8 JSON |
| `TexType.Preview.emf` | 矢量预览图 |
| `TexType.Preview.png` | 位图预览图 |

公式内容全在对象里，不存在文档变量或内容控件里（LaTeXSnipper 的 OMML 公式存在文档变量里，TexType 不这样做）。

PowerPoint 里的 OLE 对象另外在形状标签里存一份记录，TexType 读取时以标签为准。两个项目都在 PowerPoint 的 OLE 对象上写了标签；LaTeXSnipper 读取时以标签为准，因为 PowerPoint 里复制过的 OLE 对象有时读不出对象内部的数据（它的文档记录了 REGDB_E_CLASSNOTREG 错误）。Word 里以对象内部的数据为准。编号文字是对象旁边的 Word 域，记录里只存是否编号和手动编号。

对象做成独立服务程序（VisualTeX 的做法）还是进程内库（LaTeXSnipper 的做法），要测试后定，数据流不受影响。

### 公式记录

| 字段 | 内容 | VisualTeX 对应 | LaTeXSnipper 对应 |
|---|---|---|---|
| `format`、`version` | 格式名，版本号 [主, 次] | `schema`、`schemaVersion` | `SchemaVersion` |
| `id` | 公式在文档里的编号 | `formulaId` | `EquationId` |
| `source.latex` | LaTeX 源码，唯一不能重算的字段 | `latex` | `Latex` |
| `source.lines` | 编辑器里的多行，多行公式按行重新打开 | `lines` | — |
| `source.display` | 行内或行间 | `displayMode` | `DisplayMode` |
| `numbering` | 不编号 / 自动 / 手动，手动编号文字 | `numbered`、`equationTag` | `NumberingMode`、`NumberText` |
| `style` | 完整样式：字体方案、字母/希腊字母/数字字体、默认字形、中文字体、字号、颜色 | `formulaLetterFont`、`formulaFaces`、`formulaChineseFont`、`fontSizePt` | `Typography` |
| `symbols` | 用到的自定义符号的定义 | — | — |
| `layout` | 引擎和版本，自然尺寸，基线，墨迹上下边 | `renderWidthPx` 等，`baseline`，Word 定位值 | `widthPoints` 等，`baselinePoints` |
| `mathml` | 公式结构，转换时不用再开编辑器 | — | — |
| `origin` | 从什么格式转来、指纹，转回去时还原原样 | `nativeOmmlFingerprint` | — |
| `preview` | 预览图哈希和大小 | — | — |
| `created`、`modified` | 版本、平台、时间 | `createdWithVersion` 等 | — |

没有沿用的：VisualTeX 的 `title`、`codeFormat`，以及 Word 定位值（`wordInlineOlePositionPt` 等）。定位值改由 Word 加载项根据基线和墨迹上下边计算，要先和 VisualTeX 的 Word 测试对过，确认位置一样再去掉。

规则：

- 源码、样式、自定义符号决定公式。其余字段都能重新算出来。
- 预览图哈希对不上，或引擎版本比当前旧，下次编辑或更新时重画。
- 主版本相同就能读，不认识的字段忽略。主版本更高就拒绝，对象不动。
- 不认识或损坏的记录不自动修复、不改写。
- 同一文档里两条公式 `id` 相同，给后出现的那条换新 `id`。
- 记录最大 1 MB，每张预览图最大 8 MB。
- 记录保存自然尺寸，用户缩放过的大小在编辑后保留。

演示文稿里的标签：记录存在一个形状标签 `TEXTYPE.FORMULA` 里，和 VisualTeX 的 `VisualTeXMetadata` 一样。LaTeXSnipper 把数据转成大写十六进制，切成 200 字符一段，代码里没写原因。要测 PowerPoint 和 WPS 能存多长的标签值，以及会不会改变大小写：有长度上限就按上限切；大小写会变，就换一种不受大小写影响的编码。VisualTeX 的标签现在能用，不能说明大小写不变，因为它同时把记录写进替代文字，标签解不出来时读替代文字。

### 转换接口

只有一个转换请求，由主程序回答：

```text
convert(输入, 目标格式) → 输出
```

支持的格式：LaTeX、TexType 公式记录、TexType OLE 对象、TexType 图片公式、Word 原生公式、MathType 对象、MathML；输出还可以是 SVG、EMF、PNG。

所有转换都先转成 TexType 公式记录，再转成目标格式。加一种格式，只要写一个读取和一个写出。加载项只调用这个请求，自己不做转换。

例外：

- 编辑已有的 MathType 对象时，保留原来的公式数据，只改编辑改到的部分，MathType 特有的信息不丢。编辑改到的地方如果没法无损写回，原对象不动，并告诉用户。
- Word 原生公式里没有 LaTeX。每次读取都从公式结构推出 LaTeX，宏名、注释和原来的写法找不回来。
- 转回原来的格式时，如果 `origin` 的指纹还对得上，直接还原原样，不重新生成。
- 两个旧产品的公式由 `legacy-import/` 读成记录，以后删掉。这个转换由用户点一下按钮开始，不属于上面规则里禁止的自动改写。

## 8. 设置

一份设置，在 `core/settings` 定义，在主程序里改，加载项通过主程序读。分三层，范围小的优先：

1. 用户默认，可导出为预设。行内、行间公式的字号也在这里（VisualTeX 现在就是按用户存的）。
2. 文档设置，存在文档里：编号格式（VisualTeX 现在存在文档变量里）。
3. 单个公式的样式，随公式保存。

| 工具栏、符号库、公式模板 | VisualTeX 的工具栏和公式磁贴库；对照 LaTeXSnipper 的 18 类符号库补缺 |

## 12. 规则

打勾的由 `tools/check-structure.mjs` 自动检查。

- ✔ 每个部分写明自己负责什么。
- ✔ 核心库只依赖核心库。
- ✔ 界面包单向依赖。
- ✔ 产品的技术标识（标识符、OLE 类名、管道名、公式格式名和 OLE 数据流名）只写在 `product.toml`。旧产品的名字只出现在文档和 `legacy-import/`。
- ✔ 旧格式读取可以干净删除：在核心库外，只有 `app/src/legacy.rs` 用，是可选功能，每次检查都会不带它编译一遍。
- ✔ 一个文件只管一件事。超过 1000 行的源文件要么按真实的边界拆开，要么在检查脚本里写明为什么保持完整（从 MathLive、mhchem 接过来的代码保持原样）。
- ✔ 不含 Python。
- ✔ 窗口样式分层。所有自定义属性只在 `ui/editor/src/styles/tokens.css` 定义（`@layer tokens`）；`styles/base.css` 只写元素规则（`@layer base`）；其余样式都是组件旁边的 `*.module.css`，只被这一个组件引用（`@layer components`）。组件在行内只设自己的 `--local-*` 属性。不用 `!important`，不用 `:global`。改一个组件的样子只改它自己的模块。
- 加载项只调用对象模型。
- 设置、消息、公式记录只定义一次。
- 不做兼容层。版本不认识的公式记录直接拒绝。旧公式的一键转换由用户发起，不算兼容层。
- 没有功能需要，就不加新的部分。

## 13. 已定的方案和还没定的问题

2026-11-24 已确认，按这些做：

- 核心库和主程序用 Rust。
- 编辑和排版用 VisualTeX 的内核和 TeX 引擎。
- Windows 加载项以 VisualTeX 的为基础。
- Mac 版 Word、PowerPoint 用 VBA 加载项。
- Word 原生公式不在文档里留隐藏数据。
- 第一个版本先做 Windows。
- Windows 上加载项和主程序之间用命名管道。
- 给加载项画图时，主程序在一个隐藏的网页窗口里运行 TeX 引擎，和 VisualTeX 一样。

要回答的问题：

- MathType 引擎还没做到的结构：用 TeX 引擎临时画，还是暂时不允许插入成 MathType 格式。
- Word 图片公式的替代文字：继续存公式记录（和 VisualTeX 一样，读屏软件会读出一串编码），还是替代文字里放能读的 LaTeX，记录只存在标题里（标题能存多长要先测）。
- 完整版 VisualTeX 是否和 TexType 并存，是否共用设置。
- 厂商名和 `product.toml` 里的标识。名字 TexType 已定，其他值是按名字暂定的。
- 转闭源需要谁同意。仓库现在的许可证是 AGPL-3.0（建 GitHub 仓库 texbrains/TexType 时选的）。还有两处会影响闭源：MathCraft 引擎目前标的是 GPL-3.0，代码有好几位贡献者，改授权要他们都同意；自研 TeX 引擎的 Times 方案里有 GPL 字体（txfonts、newtx 数学字体），另有两组字体（RSFS、stmaryrd）VisualTeX 自己标了“发布前要确认”。MathCraft 的模型文件和 Pix2Text 在 Hugging Face 上公开的模型逐字节相同：公式识别是 breezedeus/pix2text-mfr（MIT），公式检测是 breezedeus/pix2text-mfd-1.5（页面标 MIT，但文件里写明是 Ultralytics YOLO11m，许可证 AGPL-3.0）；文字检测和识别是 PP-OCRv5（Apache-2.0）。只识别公式时只用公式识别模型。
- 旧产品里还没放进来的功能哪些进第一版：PDF 识别、手写识别、识别历史、HTTP 接口、文档解析（LaTeXSnipper），外部识别服务（两个项目都有）。

要先测的：

- MathCraft 和 VisualTeX 现用识别模型的准确率。
- OLE 公式对象在 Word、WPS 的 32 位和 64 位下的做法。
- MathType 排版引擎先做最简单的结构，看多少预览图和 MathType 的完全一致。
- 在真实的 MathType 6.9 和 7.x 上互相读写（需要一台装了这两个版本的机器）。
- Office 自带的同名旧字体会不会盖住 MathType 字体。
- 编辑带 MathType 特有信息的公式，不丢信息。
- PowerPoint 和 WPS 演示能存多长的形状标签值，会不会改变大小写；Word 图片的标题和替代文字能存多长。
- Word 加载项根据基线计算的 OLE 公式位置，是否和 VisualTeX 现在的一样。
